# 알려진 이슈

과거 사고와 미해결 이슈. 비슷한 증상을 다시 만났을 때 원인을 재조사하지 않도록 기록한다.

## ngrok 최신 버전 설치 시 Defender 오탐 (미해결, IT 사전승인 필요)

- 이 ngrok 계정은 에이전트 3.20.0 이상을 요구한다(`ERR_NGROK_121`). winget으로 설치되는 버전(3.3.1)은 이 조건을 충족하지 못한다.
- `ngrok update`로 최신 버전을 받으면 회사 Defender가 새 바이너리를 `Trojan:Win32/Kepavll!rfn`으로 오탐하여 격리한다(Go 바이너리 자동 업데이트에 흔한 오탐이지만 사내 PC에서 임의로 예외 처리하지 않았다).
- 실제 터널 운영 전 IT에 `ngrok.exe`(경로: `%LOCALAPPDATA%\Microsoft\WinGet\Packages\Ngrok.Ngrok_*\ngrok.exe` 및 갱신 파일) 허용 또는 3.20.0 이상 버전의 사전 승인을 요청해야 한다. 임의로 Defender 예외를 추가하지 말 것.

## 안양/화성 사업장별 분리 게시물 병합 로직

- 평소 식당은 두 사업장(안양·화성) 메뉴가 같아 통합 게시글 한 건으로 올라온다. **운영 예외(끼니 미운영 등)가 있는 주에만** 사업장별로 나눠 올라온다. 즉 사업장 게시글이 올라왔다면 그것이 그 주의 최종 식단표이며, 별도의 통합 게시글을 기다리지 않는다.
- 과거 사고(2026-08-24 주차): 사업장 분리 게시물 113건이 저장되어 "수집 완료" 알림이 나가고 폴링이 멈췄지만, 정작 챗봇은 공통 식단을 고르지 못해 "확인할 수 없어요"로 응답했다. 원인은 **확보 판정 기준과 응답 생성 기준이 서로 달랐던 것**. 지금은 응답을 만들 때 쓰는 것과 같은 함수(`_choose_common_menu`)로 확보를 판정하도록 고쳤다.
- 실측 비교: 두 사업장 식단을 셀 단위로 대조하면 42칸 중 31칸이 완전히 같고, 진짜 차이는 "어느 요일 조식을 쉬는가"뿐이었다(당시 안양은 화요일, 화성은 목요일 조식 미운영). 나머지 차이는 OCR 오인식이었다.
- 병합 규칙:
  - 끼니별로 운영/미운영 여부가 같으면 사업장을 밝히지 않고 하나로 합친다(코너별로 더 풍부하게 읽힌 쪽을 채택).
  - 운영 여부가 갈리는 끼니만 사업장을 나란히 보여준다(한쪽만 보여주면 다른 사업장 사용자가 닫힌 식당으로 오해할 수 있다).
  - "통합 식단표가 없어서 대신 안내한다" 같은 사정 설명은 넣지 않는다 — 판단은 서버가 끝낸다.
  - 알림 메일에는 그 주가 사업장별로 나뉘어 올라왔다는 사실을 적는다(그 자체가 "이번 주에 운영 예외가 있다"는 신호이기 때문).

## 과거 SMTP 비밀번호 유실 사고 (해결됨, 재발 방지 절차는 deployment-runbook.md 참고)

- 2026-08-21, 배포 아카이브에 `.env`를 포함시켜 서버에 올렸다가 서버에서 직접 입력해둔 `SMTP_PASSWORD`(Gmail 앱 비밀번호)가 로컬 `.env.example` 기준 값으로 덮어써졌다.
- 백업이 없어 재입력만이 유일한 복구 수단이었다.
- 재발 방지: 배포 시 `.env`는 절대 전송하지 않고, 새 키가 필요하면 서버에서 `grep` 후 append만 한다. 자세한 절차는 `knowledge/deployment-runbook.md`의 ".env는 절대 로컬로 덮어쓰지 않는다" 섹션 참고.

## PP-OCRv5 server 모델 크래시

- PP-OCRv5 **server** 감지 모델은 쓰지 않는다. Windows PC에서는 oneDNN 오류로, Linux 서버에서는 세그멘테이션 폴트로 프로세스가 죽는 것을 실측으로 확인했다.
- 두 환경 모두 mobile 감지 모델(`PP-OCRv5_mobile_det`)만 사용한다. 자세한 배경은 `knowledge/ocr-corrections.md` 참고.
