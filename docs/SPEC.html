이 문서는 cafeteria-menu-kakao-bot가 어떻게 동작해야 하는가를 정의하는 기준이다. 코드가 현재 그렇게 동작한다는 사실은 사양이 아니다. 사양과 구현이 다르면 코드에 맞춰 이 문서를 고치지 말고 SPEC / CODE MISMATCH로 식별한다 — 절차는 AGENTS.md에 있다.

프로젝트 규모에 따라 아래 Section은 줄일 수 있다. 다만 1 목적 · 2 범위 · 5 기능 요구사항 · 9 오류 처리 · 11 테스트 사양 · 12 추적성은 유지보수형 자동화라면 반드시 채운다.

1. 목적

사내 구성원이 카카오톡에서 "금요일 점심"처럼 평소 말투로 물으면, 그룹웨어 자유게시판에 이미지로만 올라오는 주간 식단표를 대신 읽어 그날 그 끼니의 메뉴를 알려준다. 사람이 게시판을 찾아 들어가 이미지를 확대해 읽는 일을 없애는 것이 목적이다.

성공 조건: 근무일(월~금) 업무 시작 시각에 그 주 식단이 DB에 들어와 있고, 카카오 질문에 실제 날짜가 명시된 메뉴 응답 또는 사유가 분명한 안내가 돌아간다.

2. 프로젝트 범위

포함

  • 그룹웨어 자유게시판에서 주간 식단 게시물과 본문 이미지 수집 (Playwright)
  • 플랫폼별 OCR provider(macOS Apple Vision / Windows·Linux PaddleOCR)로 이미지 인식
  • 표 좌표 기반으로 날짜 · 끼니(조식·중식·석식) · 코너(일반식·PLUS 코너·간편식·건강식) 구조화
  • OCR 글자 오인식과 노이즈 조각 교정
  • SQLite에 현재 주 식단 저장
  • FastAPI 카카오 Skill API로 자연어 질문 해석과 응답
  • 주말 폴링으로 다음 주 식단표를 미리 확보하고, 미확보 시 알림 메일 발송·시간별 재시도

제외

  • 과거 주·다음 주 식단 조회. 사용자에게는 현재 주만 제공한다. 1년치 과거 데이터는 OCR·파서 검증(--learning 모드) 전용이며 운영 DB와 파일을 공유하지 않는다.
  • 주말 식단. 식당을 운영하지 않으므로 안내 문구만 돌려준다.
  • 사업장별 식단 분기 응답. 공통 식단만 노출하고 지점명을 응답에 드러내지 않는다.
  • 없는 정보의 추측·생성. 식단표가 아직 없으면 지어내지 않고 사정을 그대로 알린다.
  • 카카오 유료 Event API(선제 푸시), 사용자 인증·개인화, 식단 예약·주문 기능.

4. 전체 동작 흐름

수집(월요일 08:00 정기 + 주말 폴링 + 시간별 재시도):

  1. 그룹웨어에 로그인하고 자유게시판 목록을 연다.
  2. POST_PREFIXES로 시작하는 제목의 게시물만 고른다.
  3. 게시물 본문에서 식단표로 볼 수 있는 큰 이미지의 URL을 모은다.
  4. 이미지를 내려받아 OCR한다(결과는 이미지 옆의 OCR 결과 JSON 파일에 캐시).
  5. OCR 라인의 좌표로 날짜 열 · 끼니 행 · 코너 행을 잡고 셀마다 메뉴 항목을 배정한다.
  6. 항목을 교정·중복 제거하고, 운영 수집이면 대상 주차(월~일) 밖의 항목을 버린다.
  7. 게시물 단위로 SQLite에 덮어쓴다(같은 source_post_id는 항상 교체).

응답:

  1. 카카오가 발화를 담은 Skill 요청을 보낸다.
  2. 토큰을 검사하고, 도움말 요청·식단 질문이 아닌 발화를 먼저 걸러낸다.
  3. 발화를 정규화해 날짜·요일·끼니·코너를 읽고, 모호하거나 지원하지 않는 요청이면 되묻는다.
  4. 현재 주 평일이면 DB를 조회해 끼니 → 코너 → 항목 순의 세로 목록을 만든다.
  5. 끼니별 말풍선으로 나눠 SkillResponse 2.0 형식으로 돌려준다.

목적

입력

선행 조건

계정 정보가 설정돼 있고 그룹웨어에 네트워크로 닿는다.

동작

headless 브라우저로 로그인한 뒤 자유게시판 목록을 연다. 제목이 [<사업장>] 형태로 POST_PREFIXES 중 하나로 시작하는 게시물만 대상으로 삼는다. 대상 게시물을 열어 본문의 큰 이미지(가로·세로 500px 초과, 게시판 첨부 이미지 URL 패턴)만 식단표 후보로 모은다. 제목만 필요한 경우(주말 폴링)에는 게시물 본문에 들어가지 않는 가벼운 목록 조회를 쓴다.

기대 결과

게시물 번호 · 제목 · 이미지 URL 목록이 담긴 항목의 배열.

예외 처리

  • 계정 정보가 비어 있으면 즉시 중단한다(그룹웨어에 접속하지 않는다).
  • 로그인 화면이 여러 번 리다이렉트하며 발생하는 navigation 중단 오류는 최종 화면에 도달하므로 무시하고 정착 시간을 더 준다. 그 밖의 브라우저 오류는 그대로 올린다.
  • 브라우저는 플랫폼에 맞게 고른다. Chrome이 없는 Linux 서버에서는 번들 Chromium을 쓰고, 비특권 user namespace가 막힌 환경을 위해 샌드박스를 끈다.

REQ-OCR-001 OCR 결과 공통 좌표 규약

implemented구현 src/menu_bot/ocr_provider.py테스트 TEST-OCR-001 (수동)참조됨 REQ-PARSE-001, TEST-OCR-001
변경 이력 1
  • [Unreleased] · Changed REQ-SCRAPE-001 / REQ-OCR-001: 자동화할 수 없는 이유(사내망·플랫폼별 provider)를 적은 수동 절차 TEST-SCRAPE-001 · TEST-OCR-001을 추가하고 추적성 표를 채웠다.

목적

플랫폼과 무관하게 파서가 같은 좌표 규약으로 OCR 결과를 받는다.

입력

이미지 파일 경로, OCR_PROVIDER(auto | apple_vision | paddleocr).

선행 조건

선택된 provider의 실행 환경이 갖춰져 있다(macOS는 Swift 툴체인, Windows·Linux는 PaddleOCR).

동작

auto는 macOS에서 Apple Vision, 그 밖에서 PaddleOCR을 고른다. 두 provider 모두 {"text", "confidence", "x", "y", "width", "height"} 라인 목록을 돌려주며, 좌표는 0~1로 정규화하고 원점은 이미지 좌측 하단, y축은 위로 증가한다. 좌측 상단 픽셀 좌표를 쓰는 provider는 이 규약으로 변환해 내보낸다. 인식 결과는 이미지 옆의 OCR 결과 JSON 파일에 캐시하고, 캐시가 있으면 다시 인식하지 않는다.

기대 결과

동일 이미지에 대해 provider가 달라도 파서가 같은 셀 구성·휴무/특식 판정을 얻는다.

예외 처리

  • 알 수 없는 OCR_PROVIDER 값은 오류로 중단한다.
  • PaddleOCR 모델명과 가속 옵션은 장비마다 되는 조합이 달라 코드가 아니라 환경변수로 바꿀 수 있어야 한다. 값만 비운 환경변수는 "미지정"으로 보고 기본값을 쓴다.
  • 감지·인식 모델명을 둘 다 명시한다. 하나만 지정하면 한국어 인식 모델이 조용히 바뀐다.

대상 주차는 다음 주 월요일이다. 이미 그 주차를 확보한 상태면 그룹웨어에 접속하지 않고 즉시 끝낸다. 아직이면 게시물 제목만 가볍게 읽어 대상 주차 게시물이 있는지 본다. 없으면 시도 기록만 남기고 끝낸다. 있으면 그 자리에서 이미지 다운로드·OCR·파싱·저장까지 마치고 week_start를 다음 주 월요일로 둔다. 응답은 실제 달력 날짜로 걸러지므로 주말에 미리 저장돼 있어도 월요일 전에는 노출되지 않는다.

저장된 메뉴 항목이 1건 이상일 때만 확보로 본다. 제목만 올라오고 이미지가 없거나 OCR이 아무것도 읽지 못한 경우를 성공으로 처리하면 폴링이 멈춰 그 주 식단을 통째로 놓친다.

확보되면 대상 주차당 한 번만 성공 알림을 보낸다. 상태는 대상 주차 단위로 저장하므로 주차가 바뀌면 수동 초기화 없이 자동으로 다시 확인한다.

기대 결과

상태 파일에 대상 주차 · 확보 여부 · 시도 기록(결과 구분과 사유)이 남고, 같은 주말의 남은 폴링은 그룹웨어에 다시 접속하지 않는다.

예외 처리

  • 접속·스크래핑 실패, 항목 0건은 확보로 보지 않고 사유와 함께 시도 기록에 남긴다.
  • 상태 파일이 깨져 있어도 수집을 막지 않는다 — 새로 시작한다.
  • 시도 기록은 상한을 두어 무한히 커지지 않게 한다.
  • 성공 알림 발송이 실패해도 수집 자체는 성공으로 처리한다.
  • 정기 수집이 같은 게시물을 다시 처리해도 REQ-STORE-001의 교체 저장으로 안전하다.

  • 카카오 요청을 처리하는 동안에는 그룹웨어에 로그인하지 않는다(수집 경로와 응답 경로 분리).
  • 웹훅 경로 토큰이 설정되면 불일치 요청은 본문을 읽지 않고 404로 답한다.
  • API는 루프백에만 바인딩하고, 외부 노출은 터널로만 한다.
  • 비밀번호·토큰을 로그·응답·문서·커밋 메시지에 출력하지 않는다. 발견한 Secret은 임의로 지우지 않고 노출 없이 위치만 알린다.

13. 미확정 사항

  • DEFAULT_LOCATION의 사양이 없다. 설정 항목과 CLI·API의 인자 전달 경로는 있지만 응답 생성에서 실제로 쓰이지 않는다. 사업장별 응답을 하지 않기로 한 범위(2절)와 맞물려, 이 설정을 유지할지 제거할지 확인이 필요하다.
  • 공통 식단을 고르는 기준이 코드에 고정돼 있다. 특정 사업장 이름 하나를 공통 식단으로 보고, 없으면 사업장이 한 곳일 때만 그 결과를 쓴다. 이 이름이 POST_PREFIXES의 첫 항목을 뜻하는지 고정된 값인지 문서에 없다.
  • 운영 DB에서 지난 주 데이터를 언제 지우는지 정해져 있지 않다. 저장은 게시물 단위 교체이고 조회는 현재 주로 제한되므로 사용자에게 노출되지는 않지만, 지난 주 게시물의 항목이 DB에 계속 남는다. 정리 주기·방법을 정할지 확인이 필요하다.
  • CLI ask와 카카오 API의 "아는 사업장 이름" 목록이 다르다. API는 설정값을 넘기고 CLI는 기본 목록을 쓴다. 두 경로가 같은 판정을 해야 하는지 확인이 필요하다.
  • 서버 재부팅을 통한 자동 시작은 아직 검증되지 않았다(README.md에 명시). 유닛은 부팅 시 올라오도록 등록돼 있으나 실제 재부팅 검증이 남아 있다.
