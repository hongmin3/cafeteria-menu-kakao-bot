이 문서는 cafeteria-menu-kakao-bot가 어떻게 동작해야 하는가를 정한 기준이다. 코드가 지금 그렇게 동작한다고 해서 그것이 사양이 되지는 않는다.

사양과 구현이 다르면 코드에 맞춰 이 문서를 고치지 않는다. SPEC / CODE MISMATCH로 알린다. 그 절차는 AGENTS.md에 있다.

1. 목적

사내 구성원이 카카오톡에서 "금요일 점심"처럼 평소 말투로 물으면, 그날 그 끼니의 메뉴를 알려준다. 주간 식단표는 그룹웨어 자유게시판에 이미지로만 올라온다. 이 봇이 그 이미지를 대신 읽는다.

목적은 사람이 게시판을 찾아 들어가 이미지를 확대해 읽는 수고를 없애는 것이다.

성공 조건:

  • 근무일(월~금) 업무 시작 시각에 그 주 식단이 DB에 들어와 있다.
  • 카카오 질문에는 실제 날짜가 적힌 메뉴 응답이 돌아간다. 답할 수 없으면 까닭이 분명한 안내가 돌아간다.

2. 프로젝트 범위

포함

  • 그룹웨어 자유게시판에서 주간 식단 게시물과 본문 이미지를 모은다 (Playwright).
  • 플랫폼에 맞는 OCR provider로 이미지 글자를 읽는다. macOS는 Apple Vision, Windows·Linux는 PaddleOCR이다.
  • 표 안 글자의 위치로 날짜 · 끼니(조식·중식·석식) · 코너(일반식·PLUS 코너·간편식·건강식)를 나눈다.
  • OCR이 잘못 읽은 글자와 잡음 조각을 바로잡는다.
  • SQLite에 현재 주 식단을 저장한다.
  • FastAPI로 만든 카카오 Skill API가 평소 말투의 질문을 해석해 답한다.
  • 주말 확인으로 다음 주 식단표를 미리 받아 둔다. 받지 못하면 알림 메일을 보내고 시간마다 다시 시도한다.

제외

  • 과거 주·다음 주 식단 조회. 사용자에게는 현재 주만 보여준다. 1년치 과거 데이터는 OCR·파서 검증(--learning 모드)에만 쓰고, 운영 DB와 같은 파일을 쓰지 않는다.
  • 주말 식단. 주말에는 식당을 운영하지 않으므로 안내 문구만 돌려준다.
  • 사업장마다 다른 식단 응답. 공통 식단만 보여주고, 응답에 지점 이름을 드러내지 않는다.
  • 없는 정보를 추측하거나 지어내기. 식단표가 아직 없으면 지어내지 않고 사정을 그대로 알린다.
  • 카카오 유료 Event API(먼저 보내는 푸시 알림), 사용자 인증·개인화, 식단 예약·주문 기능.

4. 전체 동작 흐름

수집은 세 가지 때에 돈다. 월요일 08:00 정기 수집, 주말 확인(폴링), 시간마다 하는 재시도다.

  1. 그룹웨어에 로그인하고 자유게시판 목록을 연다.
  2. 제목이 POST_PREFIXES로 시작하는 게시물만 고른다.
  3. 게시물 본문에서 식단표로 볼 수 있는 큰 이미지의 URL을 모은다.
  4. 이미지를 내려받아 OCR한다. 결과는 이미지 옆 OCR 결과 JSON 파일에 저장해 두고 다시 쓴다(캐시).
  5. OCR 라인의 위치(좌표)로 날짜 열 · 끼니 행 · 코너 행을 찾고, 칸마다 메뉴 항목을 넣는다.
  6. 항목을 바로잡고 중복을 없앤다. 운영 수집이면 대상 주차(월~일) 밖의 항목을 버린다.
  7. 게시물 단위로 SQLite에 덮어쓴다. 같은 source_post_id는 항상 새것으로 바꾼다.

응답:

  1. 카카오가 발화를 담은 Skill 요청을 보낸다.
  2. 토큰을 검사한다. 도움말 요청과 식단 질문이 아닌 발화를 먼저 걸러낸다.
  3. 발화를 표준 표현으로 바꾼 뒤 날짜·요일·끼니·코너를 읽는다. 애매하거나 지원하지 않는 요청이면 되묻는다.
  4. 현재 주 평일이면 DB를 조회해 끼니 → 코너 → 항목 순의 세로 목록을 만든다.
  5. 끼니별 말풍선으로 나눠 SkillResponse 2.0 형식으로 돌려준다.

5. 기능 요구사항

10. 보안 요구사항

  • 인증 수단(그룹웨어 계정, 웹훅 토큰, SMTP 앱 비밀번호)은 .env에만 둔다. 그 파일은 소유자만 쓸 수 있게 권한을 제한한다.
  • 저장소에는 .env.example의 키 이름과 형식만 둔다.
  • 저장소에 넣으면 안 되는 것: .env, 내부 주소, 계정, 원본 이미지, OCR 결과, SQLite DB, 어휘집, 게시물 목록, 터널 인증 설정, 로그.
  • 카카오 요청을 처리하는 동안에는 그룹웨어에 로그인하지 않는다. 수집 경로와 응답 경로를 나눈다.
  • 웹훅 경로 토큰이 설정돼 있으면, 맞지 않는 요청은 본문을 읽지 않고 404로 답한다.
  • API는 루프백에만 연다. 바깥 공개는 터널로만 한다.
  • 비밀번호·토큰을 로그·응답·문서·커밋 메시지에 출력하지 않는다.
  • 발견한 비밀값(Secret)은 마음대로 지우지 않는다. 드러내지 않고 위치만 알린다.

13. 미확정 사항

  • DEFAULT_LOCATION의 사양이 없다. 설정 항목이 있고 CLI·API가 이 값을 인자로 넘기는 경로도 있지만, 응답을 만들 때는 쓰이지 않는다. 사업장별 응답을 하지 않기로 한 범위(2절)와 이어지는 문제다. 이 설정을 남길지 없앨지 확인이 필요하다.
  • 공통 식단을 고르는 기준이 코드에 고정돼 있다. 특정 사업장 이름 하나를 공통 식단으로 보고, 그 이름이 없으면 사업장이 한 곳일 때만 그 결과를 쓴다. 이 이름이 POST_PREFIXES의 첫 항목을 뜻하는지, 고정된 값인지 문서에 없다.
  • 운영 DB에서 지난 주 데이터를 언제 지울지 정해져 있지 않다. 저장은 게시물 단위로 바꿔 넣고 조회는 현재 주로 제한하므로, 사용자에게는 보이지 않지만 지난 주 게시물의 항목이 DB에 계속 남는다. 정리 주기·방법을 정할지 확인이 필요하다.
  • CLI ask와 카카오 API의 "아는 사업장 이름" 목록이 다르다. API는 설정값을 넘기고 CLI는 기본 목록을 쓴다. 두 경로가 같은 판정을 해야 하는지 확인이 필요하다.
  • 서버를 재부팅했을 때 저절로 켜지는지는 아직 검증하지 않았다(README.md에 적혀 있다). 유닛은 부팅할 때 올라오도록 등록돼 있지만, 재부팅해서 확인하는 일이 남아 있다.
